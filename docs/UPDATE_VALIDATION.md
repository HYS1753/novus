# Windows 설치·업데이트 검증

## 공개 전 로컬 QA 설치본

`scripts/update-qa.mjs`는 정식 Release를 공개하지 않고 실제 NSIS 설치·업데이트·재시작을 검증하는 개발 PC 전용 도구입니다. 앱에 포함되지 않으며 정식 소스·설정·버전·개인 키를 변경하지 않습니다.

- Git 추적 중인 네이티브 파일의 현재 작업 사본을 `src-tauri/target/update-qa/<버전>/`에 복사합니다. 앱 식별자 `com.novus.hub.qa`, 제품명·실행 파일명 `novus-qa`, QA 제목으로 설치·웹뷰 프로필·설정·캐시를 정식 앱과 분리합니다.
- 현재 앱 버전과 patch가 하나 높은 버전 두 개를 빌드합니다. QA 버전은 정식 배포 버전 확정이나 Git 태그 생성이 아닙니다.
- 복사본에서만 endpoint와 허용 파일 URL을 `http://127.0.0.1:19077`로 변경하고 localhost HTTP를 허용합니다. 리다이렉트도 해당 주소·포트로 제한하며 QA 식별자가 아니면 거부합니다. 서명된 버전 필수·다운그레이드 차단·NSIS 설치본 확인·128MiB 제한·설치 전 재검증은 유지합니다.
- 복사본의 공개 키는 별도의 폐기 가능한 암호화된 QA 키입니다. 생산 키·GitHub Secrets를 읽거나 전달하지 않습니다. QA 서명은 생산 키 서명과 호환되지 않으며 QA 설치 파일을 사용자용 Release에 올리면 안 됩니다.
- 프런트엔드는 현재 `pnpm build` 결과를 별도 스냅샷으로 복사해 **상대 경로 frontendDist**로 내장합니다. Windows 드라이브 절대 경로는 Tauri에서 URL로 해석되어 파일 목록이 열릴 수 있으므로 사용하지 않습니다. MPV DLL은 고정 SHA256을 확인해 복사합니다. 네이티브 릴리즈 최적화·NSIS currentUser/passive 업데이트 경로는 정식 앱과 같습니다.
- 사본을 빌드할 때 기존 Cargo target 캐시를 재사용합니다. 정식 배포는 반드시 깨끗한 커밋에서 정식 CI로 다시 빌드합니다. QA 산출물의 이름을 바꾸어 정식 파일로 사용하지 않습니다.

```powershell
pnpm build
node scripts/update-qa.mjs prepare
node scripts/update-qa.mjs build baseline
node scripts/update-qa.mjs build target
node scripts/update-qa.mjs serve
```

`prepare`는 기존 QA 세션·키를 덮어쓰지 않습니다. `session.json`에는 출발 소스 커밋, 버전 쌍, 설치 파일의 해시·크기만 기록합니다. 실제 준비 파일은 Git에서 제외됩니다. 저장된 `sourceCommit`은 사본 생성 시 HEAD이며 커밋하지 않은 소스 변경까지 증명하는 attestation은 아닙니다.

`build`는 Tauri로 NSIS를 만든 후 QA 키로 버전을 서명하고 표준 검증기로 확인합니다. `serve`는 산출물 해시를 재확인하고 localhost의 `latest.json`과 목표 EXE 두 경로만 제공합니다. 외부 주소에 바인딩하지 않으며 설치·로그인·자동 업데이트 실행을 스스로 시작하지 않습니다. 서버 종료는 Ctrl+C입니다.

## 실행 순서와 HITL

1. 빌드된 baseline 앱의 대시보드가 정상 렌더링되는지 먼저 확인합니다. `assets/`의 baseline EXE를 사용자 확인 후 설치하고 QA 앱에서 자동 업데이트를 OFF로 설정합니다.
2. 독 위치·테마·갤러리 탐색 등 보존을 확인할 설정을 고릅니다. 로그인은 사용자가 직접 진행합니다. 비밀번호·인증 코드·쿠키 파일을 검증 기록이나 채팅으로 수집하지 않습니다.
3. 서버 오류와 수동 재시도, 느린 다운로드의 진행률·취소·캐시 정리, 변조 파일의 서명 오류를 확인합니다. 이 동안 설치 버튼을 누르지 않습니다.
4. 정상 파일을 준비하고 최종 설치 확인에서 앱 종료·NSIS 실행·재시작을 관찰합니다. 파일 버전과 설치 등록 버전, 설치 경로·uninstall.exe 존재를 확인합니다.
5. 새 앱에서 선택했던 설정과 자동 업데이트 OFF, 동일 서비스의 로그인 유지 여부를 확인합니다. Netflix 로그인·프로필 확인은 사용자 HITL로 확인하며 계정 정보나 로그인 DB를 읽지 않습니다.
6. 현재 버전에서 재확인했을 때 최신으로 표시되고 중복 설치하지 않는지 확인합니다. 자동 ON의 확인·다운로드와 OFF의 자동 요청 중지, 수동 작업 사용도 확인합니다.

서버 모드는 `src-tauri/target/update-qa/server-mode.json`의 `mode`로 선택합니다. 허용 검증 모드는 `normal`(기본), `slow`(EXE를 256KiB마다 100ms 지연), `unavailable`(503), `upToDate`(manifest 204), `tampered`(서명은 유지하고 EXE 한 바이트를 변조)입니다. 정식 앱에는 이 파일이나 모드가 없습니다.

## 검증의 한계와 공개 조건

Windows x64에서 QA 0.2.0 → 0.2.1의 실제 앱 내 업데이트를 검증했습니다. 정상 서명 파일의 다운로드·설치 확인 후 기존 프로세스가 종료되고 새 프로세스로 자동 재시작했으며, 설치 등록·실행 파일 버전이 모두 0.2.1로 변경됐습니다. 설치된 실행 파일은 NSIS 번들 식별자 패치를 정규화하면 빌드 원본과 동일합니다.

| 검증 항목      | 확인한 동작                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 설정 보존      | 라이트 모드·왼쪽 독·자동 업데이트 OFF가 업데이트/재시작 후 유지됨                                                        |
| Netflix 로그인 | 사용자가 QA 앱에서 로그인한 뒤 업데이트 후 재로그인 없이 `/browse` 콘텐츠 홈으로 접속함. 쿠키·인증 정보 파일은 읽지 않음 |
| 자동 작업      | ON 후 30초 예약 조회·자동 다운로드·진행률 표시, 다운로드 중 OFF 전환 시 대기 상태 복귀                                   |
| 수동 작업      | OFF에서도 조회·다운로드 가능, 취소 후 실제 업데이트 캐시의 임시 EXE가 0개로 정리됨                                       |
| 실패와 복구    | 서버 503 오류 후 재조회 가능, EXE 한 바이트 변조 시 서명 오류로 설치 차단, 정상 파일로 재시도 성공                       |
| 중복 설치 차단 | 업데이트 후 같은 0.2.1 manifest 재조회 시 최신 버전으로 표시하고 다운로드/설치 버튼을 제공하지 않음                      |

테마는 기존에 저장하지 않던 설정이므로 새 구현부터 localStorage `novus-theme`로 보존합니다. 저장되지 않았던 이전 실행의 테마를 소급 복원하는 기능은 아닙니다. 생산 업데이트 개인 키나 정식 Release를 사용하지 않고 QA 키·localhost 전송 경로에서 확인한 결과입니다. 실제 Surface 기기의 성능, Netflix 유료 영상 DRM 재생, 기존 MSI 이전은 이 검증 범위에 포함하지 않습니다.

QA는 실제 설치·앱 내 업데이트·재시작·데이터 보존 경로를 검증하지만 정식 GitHub HTTPS 배포 주소나 생산 키를 사용하는 설치본의 최종 다운로드까지 증명하지 않습니다. 공개 전 정식 CI의 서명·메타데이터 검증을 유지하고, 공개 승인 이후 정식 설치본에서 GitHub 배포 경로를 별도 확인합니다. 기존 0.1.0에는 updater가 없으므로 최초 전환은 수동 설치이며 MSI 이전은 별도 확인 대상입니다.

QA 확인과 소스 검증이 끝나도 태그·정식 Release 공개는 사용자 승인 범위에서 별도로 수행합니다. 승인된 배포의 실행 순서와 공개 후 GitHub 경로 검증은 RELEASING.md를 따릅니다.
