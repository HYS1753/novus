# development 디자인의 main 통합 작업계획

## 1. 목표와 범위

최종 사용자 화면은 development의 Nv 디자인 하나로 통일한다. 기존 main의 Glass UI·QuickHeader·SettingsSheet·구형 스타일가이드를 되살리거나 디자인 전환 옵션으로 병행하지 않는다. 홈·설정·온보딩·갤러리·파일·사진·영상·서비스 독·업데이트 화면 모두 같은 디자인 토큰과 입력 규칙을 사용한다.

main에서 검증·배포한 업데이트 엔진, 설치 계약, 서명 키, 게시 워크플로, 사용자 데이터 보존은 유지한다. **디자인의 기준은 development이고 기능·배포의 기준은 두 브랜치의 최신 구현을 통합한 결과**다. main을 development 스냅샷으로 강제 교체하지 않는다.

이번 문서는 소스 정적 분석과 가상 병합 결과를 바탕으로 승인받은 통합 실행 계획이다. 구현은 아래 통합 기준을 따르며 설치 검증의 절차·한계는 `UPDATE_VALIDATION.md`에 기록한다. 완료 범위는 검증 후 main 병합이며, 새 태그·Release 게시는 별도 요청에서 진행한다.

## 2. 분석 기준과 확인된 충돌

| 구분               | 기준                                                                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| main               | `d589ba064bae38d49848a22a36552592396e3baf` — 공개된 v0.2.0의 소스                                                                                    |
| origin/development | `7484f92763106f4fb469e3fc83aa3335afb960c8`                                                                                                           |
| 공통 조상          | `865d736a7617bd55daddf756e7f549b4f6f026af`                                                                                                           |
| 분기 후 커밋       | main에만 2개, development에만 33개                                                                                                                   |
| development 변경   | 공통 조상 대비 전체 258개 파일, `src/`·`src-tauri/` 170개 파일 변경. 디자인 도구·참조 자료도 포함하므로 전체 변경량이 앱 런타임 크기를 뜻하지는 않음 |

실행 전에 원격을 다시 fetch하고 이 기준이 변했으면 비교·충돌 진단을 갱신한다. 분석에서는 `git merge-tree --write-tree --name-only main origin/development`를 사용했다. Git의 임시 객체만 생성하며 main·인덱스·작업 트리는 병합하지 않았다.

| 가상 병합 충돌                                    | 처리 방향                                                                                                 |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `src/shared/hooks/index.ts`                       | development의 새 훅 export를 유지하고, main의 테마 훅을 별도 권위로 병행하지 않도록 설정 이주와 함께 정리 |
| `src/widgets/quick-header/ui/QuickHeader.tsx`     | development에서 삭제, main에서 수정된 경로. 삭제를 유지하고 테마 보존 기능은 V2 설정 모델에 반영          |
| `src/widgets/settings-sheet/ui/SettingsSheet.tsx` | development에서 삭제, main에서 수정된 경로. 삭제를 유지하고 SettingsV2/UpdateSettingsV2로 통합            |

충돌은 현재 3개지만 자동 병합 성공이 기능 통합 성공을 뜻하지 않는다. 특히 main에서만 추가한 `src/main.tsx`의 `initializeTheme()`, `shared/lib/theme.ts`, `useTheme.ts`, 테마 테스트는 자동으로 남을 수 있어 별도 의미 검토가 필요하다. 반대로 development가 공통 조상 이후 수정하지 않은 게시 워크플로·테스트 명령은 정상적인 3-way merge에서 main 변경을 유지해야 한다.

## 4. 통합 기준과 우선 보완

### 4.1 디자인은 development를 유지

- V2 토큰·Nv 컴포넌트·화면 구성·사진 프레임·오늘 화면·새 갤러리/파일/플레이어를 기준으로 삼는다.
- 기존 파란 Glass 카드나 구형 설정 시트를 업데이트 기능 때문에 복구하지 않는다.
- 삭제된 UI의 import/export, 구형 CSS 진입점, 사용하지 않는 테마 훅·스타일가이드·주석을 정리한다. 재사용 중인 일반 기능 컴포넌트까지 경로 이름만 보고 삭제하지 않는다.
- 수정하는 코드는 `@/*` 경로 별칭과 기존 계층 경계를 지킨다. 컴포넌트의 직접 invoke는 허용하지 않는다.

### 4.2 main의 배포·설치 계약 보존

- `.github/workflows/release-windows.yml`의 `publish_version` 게시 경로, `publish-release.mjs`와 회귀 테스트, `RELEASING.md`, 버전별 릴리즈 노트, QA 도구를 유지한다.
- `package.json`의 release/update 테스트 명령을 development의 오래된 명령으로 되돌리지 않는다. 기존 테마 테스트는 V2 이주 테스트로 교체할 때 함께 정리한다.
- `com.novus.hub`, `novus.exe`, Windows x64 NSIS currentUser, HTTPS endpoint, 공개 키, 서명된 버전 필수·다운그레이드 금지 및 main 전용 updater IPC를 유지한다.
- 공개된 v0.2.0 태그와 파일은 수정하지 않는다. 이 병합은 자동 배포가 아니다. 새 디자인 배포는 별도 승인 후 새 버전을 사용하며, 기능 추가 범위상 다음 minor 버전 `0.3.0`을 우선 검토한다.

### 4.3 테마·설정 이주: 실제로 필요한 수정

main의 저장 키는 `novus-theme`, development의 설정 레코드는 `novus.v2.preferences`다. 단순 병합하면 V2 기본값 system과 main 초기화가 서로 다른 값을 적용하거나 사용자의 고정 테마를 잃을 수 있다.

설정 권위는 V2 레코드 하나로 통일한다.

1. 유효한 V2 테마가 있으면 system/light/dark 선택을 그대로 사용한다.
2. V2 테마가 없을 때만 기존 `novus-theme`의 light/dark를 이주한다.
3. 둘 다 없거나 손상됐으면 development의 기본값 system을 사용한다.
4. 이주 결과를 안전하게 저장하며 실패 시 기존 값은 삭제하지 않고 현재 세션을 계속 사용할 수 있게 한다.
5. main의 별도 테마 초기화·훅은 이주 후 정리하고, V2 시작·온보딩·사진/영상 조작 창에서 같은 테마 규칙을 사용한다.

독 위치와 사진 글자 배경 강도는 development도 기존 키를 사용하므로 유지한다. 자동 업데이트 ON/OFF는 Rust의 `updater.json`이 계속 권위이며 V2 레코드로 복제하지 않는다. 사용자 로그인·WebView2 프로필·기존 미디어 탐색 기록은 초기화하지 않는다. V2 온보딩은 새 언어/자세 선택을 위한 1회 진입으로 다루고, 완료 후 재시작마다 반복되지 않게 검증한다.

### 4.4 업데이트 화면: 새로 만들기보다 V2의 기능 동등성 보완

`UpdateSettingsV2`는 이미 NvListSection/NvListRow/NvButton/NvToggle/NvStatus/NvToast와 V2 토큰을 사용한다. 기본 디자인은 유지하고 다음을 보완·검증한다.

- 동적 설치 확인 영역의 `data-autofocus`만으로는 포커스 이동이 보장되지 않는다. NvSheet의 포커스 효과는 시트를 열 때 실행되므로, 확인 영역이 나중에 생길 때 **나중에**로 포커스를 옮기고 보류하면 설치 버튼으로 복귀시킨다.
- 설정 저장 오류만 있을 때 V2는 실제 `preferenceIssue` 대신 일반 오류 문구를 보여준다. 저장 실패·자동 작업 중지·다시 저장의 관계를 명확히 표현한다. 작업 오류와 설정 오류를 혼동하지 않는다.
- NvRoot의 tablet/TV·다크/라이트·4개 언어에 맞춰 버튼 줄바꿈, 진행률·크기 미정 상태, 오류·재연결, 릴리즈 노트, 긴 버전/문구와 마지막 확인 시간을 점검한다.
- 설치 전 종료·재시작 안내와 명시적 확인, 설치 중 중복 실행 차단, 미설치 실행의 설치 차단을 유지한다.
- 홈 알림은 development의 NvToast를 유지하고 콘텐츠/온보딩/설정 위에 불필요하게 겹치지 않게 확인한다. 서비스나 영상 재생 중 자동 설치·팝업을 추가하지 않는다.
- 루트 단일 controller의 수명과 revision/취소 보호를 유지한다. 시트 닫기는 설치 확인만 해제하고 다운로드 자체를 중단하지 않는다.

### 4.5 새 네이티브 기능과 성능 검증

- autostart 의존성과 capability는 development 구현을 포함하되 updater·Tauri의 버전 고정과 IPC 권한을 유지한다. 실제 설치본에서 현재 상태 조회·변경·실패 표시를 확인하고, QA에서 바꾼 시작 등록은 원래 상태로 복원한다.
- 재귀 미디어 스캔의 20,000개/깊이 8 제한, 120초 walk cache, snapshot slot 분리, 오래된 응답 무시, EXIF 가로/세로 및 회전, 정렬/월 이동 인덱스를 회귀 검증한다.
- 프런트엔드 새 런타임 패키지는 추가하지 않는다. 실제 CSS blur가 없는지, 대시보드 DOM이 500개 미만인지, 목록이 가상화되는지 측정한다. RAM 30MB·60fps는 측정 전 달성으로 보고하지 않는다.
- 시계·영상 상태 폴링은 현재 10초 이상이다. 온보딩 PosturePreview에는 1.1초 애니메이션 interval이 별도로 있으므로 활성/숨김/감소 모션에서의 정리와 비용을 확인한다. 상태 폴링과 장면 전환 애니메이션을 구분하되, 저사양 기준을 어기면 정적/입력 기반 예시로 조정한다.
- 문서의 과거 v1 bridge/미구현 설명은 실제 제거된 코드와 일치하도록 정리한다. 개발 fixture·디자인 도구가 정식 번들에 포함되지 않는지도 확인한다.

## 5. 실행 순서와 단계별 완료 조건

| 단계                        | 작업                                                                                                                                  | 다음 단계로 넘어갈 조건                                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 1. 기준 고정                | 최신 main/development를 재확인하고 main 기반 `codex/development-v2-integration` 브랜치 생성. development 자체의 기본 검사 결과도 확보 | 브랜치 SHA·기존 실패·변경 범위가 구분됨                                                                        |

| 4. 기능/화면 검증           | 홈·서비스·미디어·파일·OS 기능·업데이트의 아래 검증표 실행. 검증으로 드러난 통합 문제만 수정                                           | 모든 필수 검사가 통과하고 실제 Windows 동작의 실패가 남지 않음                                                 |
| 5. 이전 버전 → V2 QA        | 기존 디자인이 실행되고 기존 테마/독/로그인이 저장된 설치본에서 새 V2 QA 버전으로 실제 업데이트                                        | 재시작 후 새 UI·설정 이주·로그인·네이티브 재생이 정상                                                          |
| 6. 문서·최종 리뷰·main 병합 | ARCHITECTURE/HANDOVER/PERFORMANCE_GUIDE 및 업데이트/검증 문서를 실제 구현에 동기화. 검증된 커밋을 main에 병합·Push                    | 깨끗한 작업 트리, development 포함 이력, 기본 GitHub 서명 빌드 성공. 공개 Release는 별도 승인 전 생성하지 않음 |

가상 병합 결과만으로 빠르게 main에 넣지 않는다. 단계 2에서 화면을 섞어 충돌을 줄이거나, 단계 4에서 기존 디자인으로 되돌려 검사를 통과시키는 방식은 사용하지 않는다.

## 6. 검증표

### 자동 검사

필수 순서를 유지한다.

```powershell
pnpm typecheck
pnpm lint
pnpm format:check
pnpm build
pnpm release:test
pnpm update:test
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo test --manifest-path src-tauri/Cargo.toml --locked --lib
```

추가 회귀 테스트는 테마 이주·동적 설치 확인 포커스·미디어 slot/정렬/월 인덱스처럼 기능 유실을 막는 항목에 집중한다. 기존 테마 테스트가 UI와 연결되지 않은 구형 모듈만 검사하는 상태로 남지 않게 한다. 이전 UI import와 CSS 진입점 검색도 함께 수행한다.

### 설치본 이전 검증의 주의점과 HITL

현재 `update-qa.mjs`는 같은 소스의 버전 두 개를 만드는 도구다. **이 방법만으로는 구형 디자인의 저장값이 V2로 옮겨지는지 증명할 수 없다.**

- 검증된 기존 QA 0.2.1 설치본·프로필이 남아 있으면 구형 테마/독/Netflix 로그인 상태를 확인해 출발점으로 재사용한다. 같은 QA 식별자·키로 더 높은 V2 QA 타깃을 준비할 수 있도록 도구를 보완한다.
- 출발점이 없으면 v0.2.0 태그 소스의 구형 UI와 통합 소스의 V2 UI를 각각 빌드하는 QA 쌍을 만든다. 각 소스의 프런트엔드를 따로 빌드해야 하며 현재 V2 dist를 양쪽에 넣으면 이전 검증이 아니다.
- QA의 키·식별자·localhost 서버와 정식 키·`com.novus.hub`·GitHub endpoint를 분리한다. 기존 QA 프로필이나 로그인 데이터를 삭제해 테스트를 준비하지 않는다. 프런트엔드는 상대 경로로 내장한다.
- Netflix 재로그인/인증이 필요하면 사용자가 직접 진행하며 비밀번호·인증 코드·쿠키 파일을 요청하거나 읽지 않는다. 실제 설치 실행에 도구의 실행 시점 승인이 필요하면 검증된 파일·버전이 준비된 뒤 HITL로 안내한다.
- 인증된 Actions 실행 수단이 없으면 사용자에게 기본 Run workflow(main, `publish_version` 비움)를 요청한다. 이 통합 검증에서 정식 게시 입력은 사용하지 않는다.

## 7. 완료 기준

- development 디자인이 모든 사용자 화면의 단일 구현이며 삭제된 Glass UI와 구형 스타일가이드가 되살아나지 않는다.
- main의 배포·게시·서명·updater 보안 계약과 기존 테스트가 유지된다.
- 기존 테마·독·업데이트 ON/OFF 및 서비스 로그인 데이터가 유지되고 V2 설정을 덮어쓰지 않는다.
- 업데이트 UI의 필수 상태와 설치 포커스가 Nv 디자인·입력 규칙 안에서 정상 동작한다.
- 새 미디어/OS 기능을 포함한 필수 검사와 Windows 회귀 검증이 통과한다. 확인하지 못한 하드웨어 항목은 성공으로 기재하지 않는다.
- 문서는 병합된 실제 구현을 설명하고 main에는 검증된 통합 커밋만 반영한다. 이미 공개한 v0.2.0은 변경하지 않는다.
