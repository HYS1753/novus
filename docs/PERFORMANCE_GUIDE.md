# Novus Low-Spec Performance Guide

> **타깃 기기 프로필**: Microsoft Surface Pro 4 (Intel Core m3-6Y30 듀얼코어, Intel HD 515, **4GB LPDDR3 RAM**, 12.3인치 2736x1824 고해상도 터치 디스플레이)

---

## 1. 저사양 디바이스 성능 도전 과제

1. **극히 제한된 RAM (4GB)**: Windows 10/11 OS 자체 점유율만 2~2.5GB에 달하므로, 앱 단독 메모리 사용량을 **30~50MB** 이내로 엄격히 통제해야 합니다.
2. **저전력 듀얼코어 CPU (4.5W TDP)**: 잦은 JavaScript 가비지 컬렉션(GC)이나 반복적인 DOM 리플로우가 발생하면 즉시 프레임 드랍(Jank)이 발생합니다.
3. **고해상도 디스플레이 (2736x1824)**: 픽셀 수가 많아 무거운 CSS 필터(blur, 복잡한 box-shadow 등)를 남발하면 내장 그래픽(HD 515)에 과부하가 걸립니다.

---

## 2. 프론트엔드 최적화 5대 원칙

### ① 무거운 CSS 필터 금지 및 GPU 하드웨어 가속 강제

- `backdrop-filter: blur(...)`는 구형 인텔 내장 GPU에서 치명적인 렌더링 지연을 유발합니다. 기본 머티리얼 강도 `0`에서는 이 속성을 **한 곳도 출력하지 않으며**, 면의 깊이는 불투명 틴트 + 헤어라인 엣지 + 스펙큘러 하이라이트로 표현합니다.
- 프로스팅은 `html[data-frost]` 스코프에서만 적용되는 opt-in 기능입니다. 강도가 0보다 클 때만 이 속성이 붙으므로, `blur(0px)`로 인한 불필요한 레이어 승격도 발생하지 않습니다. 컴포넌트에 `backdrop-filter`를 직접 쓰지 말고 역할 토큰(`--material-blur-control` / `-panel` / `-overlay`)을 통해서만 노출하십시오.
- 프로스팅을 켜는 경우 동시에 화면에 존재하는 블러 레이어 수를 8개 미만으로 유지하고, 블러값 자체를 애니메이션하지 않습니다.

### ①-1 모션은 transform / opacity 로만

- 모든 인터랙션은 6개 모션 레시피(`press` · `lift` · `reveal` · `emerge` · `enter` · `pulse`) 중 하나로만 표현하며, 컴포넌트는 duration을 직접 선언하지 않습니다.
- 레이아웃 속성(`width`, `height`, `top`, `margin`)과 컬러 램프, 블러 반경은 애니메이션 대상이 아닙니다. 리플로우/리페인트 비용이 프레임 예산을 넘깁니다.
- 반복 모션(스켈레톤 시머, 무한 진행바)은 화면당 필요한 최소 개수만 두고, `prefers-reduced-motion: reduce`에서는 전역 규칙으로 완전히 정지합니다.
- 모션/트랜지션이 있는 모든 인터랙티브 요소(버튼, 카드)에는 반드시 `transform: translateZ(0)`를 부여하여 독립 컴포지팅 레이어로 승격시킵니다.
- 위치 이동이나 크기 조절은 `top`, `left`, `width`, `height` 대신 항상 **`transform: translate(...)` 및 `scale(...)`**만을 사용합니다.

### ② 저빈도(Low-frequency) 타이머 및 백그라운드 절전

- 시계/날짜 위젯은 1초 단위(`1000ms`)가 아닌 **10초 또는 30초 단위**로만 인터벌을 실행합니다 (`src/shared/hooks/useCurrentTime.ts` 참조).
- 창이 최소화되거나 비활성화되면 백그라운드 애니메이션 및 폴링을 즉시 일시정지합니다.

### ③ DOM 노드 수의 최소화 및 가상화(Virtualization)

- 렌더링 트리에 존재하는 총 DOM 노드 수를 500개 미만으로 억제합니다.
- 긴 앱 목록이나 동영상 리스트를 표시할 때는 전체를 렌더링하지 않고 화면에 보이는 요소만 렌더링하는 가상 스크롤(Virtual Shelf) 방식을 적용합니다.

### ④ 44px 이상의 터치 타겟과 즉각적인 Active 피드백

- 윈도우/태블릿 환경에서 손가락 터치 시 빗나가지 않도록 모든 터치 버튼 및 카드는 **최소 48x48px** 이상의 터치 영역을 보장합니다 (`--touch-target-min`).
- 터치 시 지연감(300ms delay)을 방지하기 위해 `-webkit-tap-highlight-color: transparent`를 전역 적용하고, `:active` 상태에서 즉각적인 `scale(0.96)` 반응을 제공합니다.

### ⑤ 가벼운 번들 사이즈 유지 (Zero Bloatware)

- Moment.js, Lodash, 대형 UI 라이브러리(Material UI, Ant Design) 도입을 엄격히 금지합니다.
- 유틸리티는 순수 JS 및 `src/shared/lib/`의 경량 함수를 사용하고, UI는 자체 제작한 순수 CSS 기반 `src/shared/ui/` 컴포넌트를 사용합니다.

### ⑥ 대용량 미디어 렌더링 및 디코딩 메모리 방어 원칙

- **원본 이미지 DOM 마운트 금지**: 사진 원본을 직접 `<img src>`로 넣지 않습니다. 격자에는 320px 썸네일, 뷰어에는 320→1600px 단계 이미지를 쓰며 확대 시에만 3200px를 요청합니다. 다만 Rust `image::open`의 원본 전체 디코딩으로 생기는 순간 메모리는 아직 측정 대상입니다.
- **현재 이미지 1장 유지**: 풀스크린 이미지 뷰어(`FullscreenImageViewer`)는 현재 사진 한 장만 DOM에 유지합니다. 다음 사진은 제한된 요청 큐에서 미리 준비하며 프런트엔드 Base64 URI 캐시는 문자열 길이 합계 12MiB로 제한합니다. 이는 실제 JS 힙 사용량의 상한과 같지 않습니다.
- **목록 마운트 상한**: 갤러리는 가상 격자로 현재 보이는 행과 위아래 1행만 렌더링하고, 스크롤 끝에 가까워지면 Rust 스냅샷에서 80개씩 추가로 받습니다. 정확한 전체 정렬을 위한 첫 폴더 메타데이터 스캔은 여전히 필요합니다. 파인더는 40개 단위 페이지를 사용합니다. 갤러리 스크롤 이벤트는 `requestAnimationFrame`으로 묶습니다.
- **썸네일 작업·디스크 상한**: 프런트엔드 요청은 최대 2개 동시 실행하며 같은 요청을 합칩니다. 앱 캐시 디렉터리의 JPEG 캐시는 첫 생성과 이후 32회 생성마다 용량을 확인해 256MiB 초과분을 오래된 파일부터 지웁니다. 이 상한과 실제 디코딩 중 메모리 사용은 Surface Pro 4에서 확인해야 합니다.
- **탐색 복원 비용**: 갤러리와 파인더는 이미지·파일 목록을 저장하지 않습니다. `localStorage`에는 현재 경로와 최대 50개 방문 경로만 기록하고, 재진입 시 해당 폴더를 다시 스캔합니다.
- **긴 경로 표시**: 브레드크럼은 현재 폴더와 바로 위 폴더만 기본 렌더링하고 나머지는 메뉴 안에 두어 툴바 너비가 길이에 따라 늘어나지 않게 합니다.
- **대시보드 가장자리 여유**: 카드 확대가 스크롤 영역에서 잘리지 않도록 스크롤 콘텐츠 내부에 좌우 여백을 둡니다. 상하 스크롤 안내에는 GPU 블러 대신 단색 그라데이션을 사용합니다.
- **홈 복귀 시 상태 재계산**: 대시보드가 다시 마운트되면 스크롤 영역의 실제 위치를 페인트 전에 다시 읽어 상단 그라데이션이 이전 화면 상태로 남지 않게 합니다.
- **인앱 하드웨어 미디어 경로 우선**: Windows에서 DLL이 확인되거나 macOS에서 묶인 dylib가 실제로 로딩되면 네이티브 libmpv 표면을 사용합니다. 엔진이 없는 환경에서는 WebView2/WebKit의 `<video>`를 사용합니다. 재생 오류 시 사용자 선택으로 설치된 MPV 또는 OS 기본 플레이어를 열 수 있습니다.
- **Windows 네이티브 플레이어 시제품**: `libmpv` DLL이 앱 리소스에 있는 경우에만 Win32 자식 영상 창을 지연 생성하고 `hwdec=auto-safe`로 디코딩을 시도합니다. 영상은 DOM이나 Base64 IPC를 거치지 않습니다. 닫을 때 디코더 스레드와 자식 창을 해제합니다. DLL은 아직 번들되지 않았으며 실제 Surface Pro 4의 하드웨어 디코딩·메모리 사용량은 미측정입니다.
- **macOS 네이티브 플레이어 시제품**: 유효한 dylib가 있을 때만 메인 스레드에서 NSView를 지연 생성하고 libmpv에 연결합니다. 지원 확인은 백그라운드에서 한 번만 실행합니다. 닫을 때 재생 스레드를 끝내고 NSView를 제거합니다. dylib와 의존 파일은 빌드 시 별도 스테이징하며 Git에는 저장하지 않습니다. 실제 영상 출력과 메모리 회수는 미측정입니다.
- **기기 정보 1회 수집**: 운영체제·CPU·총 RAM·모델 등 정적 기기 정보는 앱 시작 시 Rust가 한 번만 읽고 Tauri State에 보관합니다. 설정 화면은 캐시된 값을 사용하며 시스템 정보 폴링이나 고빈도 타이머를 추가하지 않습니다. GPU와 코덱별 디코더 기능은 아직 자동 탐지하지 않습니다.
- **아이콘 모션 단일 경로**: 아이콘 효과는 `MotionIcon` 프리셋만 사용하며 `transform`과 `opacity`만 변경합니다. 반복 모션은 진행 중 상태에만 활성화하고 `prefers-reduced-motion`에서 즉시 중단합니다.

## 3. 메모리 누수 방지 체크리스트

로컬 동영상의 코덱별 재생 성능과 네이티브 엔진 통합 검증 절차는 [`VIDEO_PLAYER_VALIDATION.md`](VIDEO_PLAYER_VALIDATION.md)에 정의합니다. libmpv가 감지된 개발 환경에서는 네이티브 경로를 선택하지만, 실제 화면 출력과 성능 결과는 아직 측정되지 않았습니다.

- [ ] `useEffect` 내부에서 생성된 이벤트 리스너, 타이머, Tauri 이벤트 언리스너가 cleanup 함수에서 100% 해제되는가?
- [ ] 대용량 이미지 자산을 직접 번들링하지 않고, SVG 아이콘 또는 최적화된 WebP/AVIF를 사용하는가?
- [ ] 개발자 도구 Performance 탭에서 60fps가 안정적으로 유지되는가?
- [ ] 이미지 갤러리 진입 시 수백 장의 파일이 있어도 렌더러 메모리 점유율이 60MB 이하로 억제되는가?
